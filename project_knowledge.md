# MCU Trim-Code Predictor: project notes

These notes are the only source of facts for the project assistant. All numbers come from the project's own experiments.

## 1. The big picture

### What is this project about?
Microcontroller chips are never perfectly identical after manufacturing. A few circuits inside each chip (a reference voltage, an internal clock and a voltage regulator) come out slightly off their targets. In the factory each chip is fine-tuned, which is called trimming. Today this is done by a trial-and-error (binary) search that takes about 20 test steps per chip (on average about 6.6 steps for the bandgap, 7.6 for the HSI oscillator and 5.6 for the LDO, 19.8 in total in the dataset). This project predicts the best trim code for each circuit directly from measurements taken before trimming, so the factory can make one educated guess and verify it instead of searching. The final result is a trained machine learning model, a Streamlit web app and this assistant.

### What is trimming and what are fuses?
Trimming means adjusting a circuit after manufacturing so that it hits its target value. The adjustment is set by a trim code, a small whole number. The codes of a chip are stored permanently in one-time-programmable fuses (a 64-bit fuse word), so they cannot be changed after they are burned. This is why predictions must be verified on the tester before burning.

### What are the bandgap, the HSI oscillator and the LDO?
- Bandgap reference: makes a very stable reference voltage. Target 1.200 V. Its trim code is 6 bits (0 to 63), the centre code 32 means no adjustment, and each step is about 2 mV.
- HSI oscillator: the chip's internal high-speed clock. Target 16 MHz. Its trim code is 7 bits (0 to 127), centre 64, and each step is about 0.2 percent of the frequency.
- LDO (low-dropout regulator): supplies a steady core voltage. Target 1.100 V. Its trim code is 5 bits (0 to 31), centre 16, and each step is about 5 mV.

### What are process-monitor (PCM) readings?
Process monitors are tiny test structures next to the chips that record how the factory process behaved for that part of the wafer. The dataset has five: NMOS threshold voltage, PMOS threshold voltage, sheet resistance, oxide thickness and relative carrier mobility. They act like a birth certificate of the chip and help correct the prediction, especially for the HSI oscillator.

### What are the chip types MCU-A, MCU-B and MCU-C?
They are three versions (derivatives) of the microcontroller. MCU-A is 75 percent of the dies, MCU-B 15 percent and MCU-C 10 percent. MCU-C is the smaller derivative.

## 2. The data

### What does the dataset contain?
8,420 dies (rows) and 42 columns from 20 wafers in 5 lots (MA1, MA2, MA3, MB1, MC1). The data is synthetic: it was generated by a script that came with the project, which models realistic chip behaviour. Each row is one chip with its position on the wafer, process-monitor readings, untrimmed measurements, the best trim codes, post-trim results, pass or fail outcomes and the fuse word.

### How was the data cleaned and quality-checked?
The data was already clean: no missing values, no duplicate rows, no repeated die ids, all trim codes inside their bit ranges, all fuse words valid 64-bit hex values and all physical values positive. Outliers were inspected but not deleted because they are real, rare chip behaviour (for example sram_fail_bits is mostly zero so any failure looks unusual). The main preparation work was assigning every column a role (input, answer, or not allowed) and controlling data leakage.

### What is data leakage and how was it avoided?
Leakage means giving the model information that secretly contains the answer. The fuse word (fuse_map_hex) matched the trim-code columns 100 percent, so it contains the answer. Columns measured after trimming (the trimmed and final voltages and frequencies, and the pass flags) are also consequences of the answer. All of them were excluded. The model only sees values known before trimming.

### What were the main findings of the exploratory data analysis (EDA)?
- Each trim code is almost a straight-line function of its own raw measurement (correlation about -0.997 for bandgap, -0.996 for HSI, -0.991 for LDO).
- Simple arithmetic from the step sizes already gets the bandgap (99.6 percent) and LDO (99.9 percent) within plus or minus 1 code, but the HSI only about 54 percent with a straight-line formula. The HSI relationship is curved.
- Lots differ a lot. For example the average HSI code is about 34 in lot MA1 and about 80 in lot MA3. This is why data must be split by wafer, not randomly.
- Position on the wafer has almost no straight-line link with the codes.
- Outcomes are very imbalanced: 99.6 percent of chips pass the sort test and only 30 chips (0.36 percent) have a latent defect. The LQFP100 package drifts the most after packaging (about 3.6 mV on the bandgap) and has the lowest final pass rate (about 90.6 percent).

## 3. The model

### Which model did you choose, and why?
One Random Forest regressor per target (bandgap, HSI, LDO), each trained to predict the correction to a physics estimate. Reasons: the relationship between a measurement and its best code is smooth but curved, which tree ensembles fit with almost no tuning while linear models fail on HSI. On wafer-grouped validation the Random Forest was best on all three targets. It is stable, trains in seconds and needs no scaling. With only 8,420 rows and about 10 numeric inputs, deep learning would add complexity and no benefit. The codes are ordered numbers, so regression (then rounding to a valid code) is better than classification.

### How does the physics estimate work, and why predict the correction?
The step size of each code is known: bandgap code = 32 + (1.200 - measured volts) / 0.002; HSI code = 64 + (16 / measured MHz - 1) / 0.002; LDO code = 16 + (1.100 - measured volts) / 0.005. This arithmetic already solves bandgap and LDO almost completely, so the forest only learns the leftover correction (best code minus physics estimate). Benefits: an easier learning task, sensible behaviour for unusual chips (a forest alone cannot extrapolate beyond the values it has seen) and an easy explanation.

### Which models were compared and what were the results?
Wafer-grouped 5-fold cross-validation on the training wafers, share of dies within plus or minus 1 code:
- Bandgap: physics only about 99.7 percent, Random Forest about 99.9 percent, HistGradientBoosting about 97.5 percent (worse than the plain formula).
- HSI: Random Forest 80.5 percent, HistGradientBoosting 80.2 percent, ExtraTrees about 76.6 percent, GradientBoosting about 76.0 percent, Ridge (linear) about 69.9 percent, physics formula only about 67.2 percent.
- LDO: almost all models about 99.7 to 100 percent.
HistGradientBoosting was only run with default-style settings, so it is not claimed to be worse in general.

### What inputs does the model use?
Eight numbers plus the chip type: the three untrimmed measurements (bandgap, HSI, LDO), the five process-monitor readings, and the chip type as two 0/1 flags. Die position (die_x, die_y, x_mm, y_mm, radius_mm) and sram_fail_bits were tested and gave no gain, so they were removed, which also keeps the app simple.

### What are the model settings?
Each forest has 300 trees. Bandgap and HSI use min_samples_leaf 3 and max_features 1.0. LDO uses min_samples_leaf 20 and max_features 0.7. They were chosen by a small grid search with wafer-grouped cross-validation on the training wafers only.

### How was the model validated?
The data was split by wafer. One random wafer from every lot (5 wafers, 2,105 dies) was held out as a final test and scored once. Model comparison and tuning used wafer-grouped 5-fold cross-validation on the remaining 15 wafers. After that the same recipe was retrained on all 20 wafers and saved. On top of that, the saved model was tested on a completely new dataset generated with a different random seed (new lots it had never seen).

### Which inputs matter most?
Permutation importance on the held-out wafers: for HSI the untrimmed HSI frequency matters most (error rises by about 0.44 codes when shuffled) and the oxide thickness reading is second (about 0.18). For the bandgap the untrimmed bandgap matters most (about 0.07) followed by carrier mobility (about 0.03). For the LDO the untrimmed LDO voltage matters most (about 0.11). Chip type had almost no effect.

## 4. Results

### What accuracy did the model achieve?
Share of dies within plus or minus 1 code of the best code:
- Held-out wafers (from lots seen in training): bandgap 99.95 percent, HSI 82.3 percent, LDO 100 percent. Exact match: 83.3, 50.6 and 89.4 percent. Mean absolute error: 0.17, 0.72 and 0.11 codes.
- Brand-new dataset with new lots (random seed 777): bandgap 99.89 percent, HSI 75.9 percent, LDO 100 percent.
By chip type on the held-out wafers the HSI within plus or minus 1 was 83.6 percent for MCU-A, 83.1 percent for MCU-C and 77.4 percent for MCU-B (MCU-B had a single test wafer, so that number is based on few dies).

### How much test time does it save?
With the dataset's own counting rule (exact prediction needs 1 check, off by one needs 2, otherwise fall back to the full search), the average on the held-out wafers was about 4.8 checks per chip (1.17 for bandgap, 2.56 for HSI, 1.11 for LDO) compared with about 19.8 for the old search, roughly 75 percent fewer. On new lots the saving would be smaller because the HSI accuracy is lower.

### How does it compare with the baseline that came with the dataset?
A baseline-style HistGradientBoosting model (predicting the code directly) was retrained on the same training wafers and scored on the same test wafers. On HSI the two are essentially tied (82.4 percent for the baseline-style model versus 82.3 percent for this model). On bandgap this model is slightly better (99.95 versus 99.52 percent) and it has a lower mean error on all three targets. The improvement is modest. The main advantages are the physics base, input checks, range warnings and the confidence signal.

### Why is the HSI harder than the bandgap and the LDO?
Its measurement is noisy. A single smooth curve of the untrimmed HSI frequency already explains about 79 percent, and what is left over is almost uncorrelated with every other column, so roughly 80 to 82 percent within plus or minus 1 is close to the ceiling for this data. The HSI relationship is also curved, which linear models cannot follow.

### What does the confidence signal mean?
The forest is 300 trees. The spread of their predictions (how much they disagree) is a rough confidence signal. On the held-out wafers dies with low spread were within plus or minus 1 code 98.9 percent of the time for HSI, medium spread 90.6 percent and high spread 57.2 percent. On the brand-new dataset the three groups scored 97.0, 73.6 and 57.1 percent. It is not a calibrated probability. It is only shown for HSI because bandgap and LDO are almost always right.

### What are the limitations?
- The data is synthetic and covers only three chip types; real silicon would need re-validation and retraining.
- HSI accuracy depends on how similar a new lot is to the training lots: about 82 percent on held-out wafers from known lots but about 76 percent on a dataset with new lots.
- MCU-B has lower HSI accuracy (77.4 percent) on its single held-out wafer.
- The tree-spread is not a calibrated probability.
- The model is a decision-support tool. Fuses are permanent, so predictions must be verified on the tester before burning.
- The input checks only catch out-of-range values and unknown chip types; the model cannot know about completely new chip designs.

### How could the model be improved?
Per-lot calibration (measure a few dies of each new lot with the old search and use them to shift the predictions), more real production data, leave-one-lot-out validation to measure new-lot performance more precisely, calibrated uncertainty (for example conformal prediction), and monitoring for drift once the model is in production.

## 5. System, deployment and the assistant

### Is the model offline or online?
The trim model is an offline model: it is trained once on historical data, saved to a file (joblib) and run locally with no internet and no learning after deployment. This is simple, fast, deterministic and easy to validate before anything is burned into a chip. It would be retrained offline when new data arrives. The chat assistant is the opposite: it uses an online large language model (LLM) through an API for language understanding, with an offline fallback that answers from these notes when no API key or internet is available.

### What is the end-to-end flow of the project?
Requirements (predict trim codes from pre-trim data to cut test time) leads to effective prompt generation (clear prompts describing the goal, data and constraints for the AI coding assistant), then code development (EDA notebook, model training notebook, shared module, Streamlit app, assistant), then testing (wafer-grouped cross-validation, one-time hold-out test, a fresh-seed dataset, automated app tests, input-validation tests) and finally deployment (a saved model plus a Streamlit app; hosting online is the next step).

### How does the app work?
The Streamlit app has a Single die tab (enter eight measurements and the chip type, see the three predicted codes, an HSI confidence meter, a how-it-was-made breakdown and a plain-English explanation), a Batch tab (upload a CSV, download predictions, and see accuracy if the true codes are included), an About tab and this assistant. The app loads the saved model through a shared TrimPredictor class which validates inputs (missing columns, unknown chip type, empty or negative values) and warns about inputs outside the training range. The same class and feature code are used in training and in the app, so there is no mismatch between training and serving.

### How does the assistant work?
It is a retrieval-grounded LLM assistant. These project notes and the current die from the Single die tab are placed in the prompt, and the LLM is told to answer only from them, to say when something is not covered, never to invent numbers and to stay on topic. Answers stream into the chat. If no API key is configured, the internet is down or the per-session question limit is reached, an offline mode finds the most relevant section of these notes using TF-IDF text similarity and shows it. The assistant only explains; it never changes the model or its predictions. A pretrained LLM is used through an API; no LLM was trained from scratch for this project.

## 6. Likely interview questions

### Q: Why did you not use deep learning?
The data is small (8,420 rows) and tabular with about 10 numeric inputs. Tree ensembles are strong on that kind of data, train in seconds and are easy to explain. A neural network would add complexity, tuning and risk of overfitting without a clear accuracy gain.

### Q: Why regression instead of classification?
Trim codes are ordered numbers: code 40 is closer to 41 than to 10. Regression uses that ordering and the result is rounded to the nearest valid code. HSI alone has 114 different codes, so classification would split the data into many tiny classes.

### Q: Why did you split by wafer?
Dies on the same wafer share factory conditions, so a random split would let the model recognise wafers and overstate accuracy. In production the model sees new wafers, so the test must too. One wafer from every lot was held out to keep all chip types in the test set.

### Q: Why within plus or minus 1 code?
One code is one small step (2 mV, 0.2 percent or 5 mV), so a one-code miss costs one extra check instead of a full search. It also matches the way the dataset's baseline counts checks.

### Q: How do you know the model generalises to new data (interview answer)?
Selection and tuning used cross-validation on training wafers only. The final test wafers were scored once. A completely new dataset with a different random seed was also tested, and that is where the honest weakness showed: HSI dropped from about 82 to about 76 percent on new lots, while bandgap and LDO stayed near 99.9 to 100 percent.

### Q: Is it safe to burn fuses based on this model?
Not blindly. Fuses are permanent. The model is decision support: the predicted codes should be verified on the tester first, and low-confidence HSI predictions should fall back to a short search.

### Q: What would you do with more time?
Per-lot calibration, real production data, leave-one-lot-out validation, calibrated uncertainty, a monitoring and retraining pipeline, and hosting the app with logging.

### Q: What if a new chip type arrives?
The model has never seen it, so it must be re-validated and probably retrained. The app rejects unknown chip type names and warns when measurements are far outside the training range, but it cannot judge a new design by itself.

### Q: What is the difference between offline and online models here?
The trim model is offline (trained once, saved, runs locally, no learning in production). The assistant uses an online LLM through an API, with an offline fallback built from the project notes.

### Q: How did you use AI tools while building this?
Prompts described the goal, data, constraints and expected output for each stage (EDA, modelling, app, assistant). The results were checked with real experiments (hold-out test, fresh-seed dataset, automated tests), and wrong or overstated claims were corrected, for example wording in the notebook and two app bugs found during testing.

## 7. Machine-learning ideas used in this project (general background)

### What is machine learning, and what kind of problem is this?
Machine learning means letting a computer learn a pattern from many examples instead of writing the rules by hand. Here each example is one chip: the inputs are its measurements before trimming and the answer is its best trim code. This is supervised learning (the examples come with the right answers) and, because the answer is a number, it is a regression problem. In this project three separate models are trained, one for each trim code.

### What are features, targets and a training set?
A feature is one input number given to the model (for example the untrimmed HSI frequency). A target is the answer we want to predict (for example the best HSI trim code). The training set is the part of the data the model learns from, and the test set is data kept hidden to check how well the model works on chips it has never seen. In this project the features are the three untrimmed measurements, the five process-monitor readings and two chip-type flags; the targets are the three best trim codes.

### What is a decision tree and what is a Random Forest?
A decision tree answers a prediction by asking a chain of yes/no questions about the inputs (for example "is the untrimmed frequency above 16.2 MHz?") until it reaches a number. One tree can be unstable, so a Random Forest builds many trees, each on a slightly different random sample of the data, and averages their answers. Averaging cancels out the individual mistakes. This project uses 300 trees per forest. A forest cannot predict values outside the range it saw in training, which is one reason this project predicts a correction to a physics estimate instead of the raw code.

### What is overfitting (over-fitting, memorising the training data)?
Overfitting means a model has memorised the training examples, including their random noise, instead of learning the real pattern. An overfitted model scores very well on training data and badly on new data. The cure is to measure performance only on data the model has not seen and to keep the model simple enough. This project guarded against overfitting with wafer-grouped cross-validation, a one-time hold-out test and a brand-new dataset; the new dataset showed HSI accuracy falling from about 82 to about 76 percent, the honest sign of the lot-to-lot risk.

### What is cross-validation and what does wafer-grouped mean?
Cross-validation splits the training data into several parts (folds) and takes turns using one fold for checking and the others for learning, so every chip is used for checking once. Here it is 5-fold and grouped by wafer, meaning all chips from one wafer are always in the same fold. This stops the model from being tested on chips whose neighbours it already learned from, which would make the score look better than it really is.

### What is hyperparameter tuning and what is a grid search?
Hyperparameters are settings chosen before training, such as the number of trees or the minimum number of chips in a leaf. A grid search tries a small table of combinations and keeps the best according to cross-validation. In this project it was done on the training wafers only, so the test wafers stayed untouched. The chosen settings are listed in the model-settings section.

### What are MAE and "within plus or minus 1 code"?
Mean absolute error (MAE) is the average distance between the predicted code and the best code, measured in code steps. For example an MAE of 0.72 for HSI means the prediction is on average less than one step away. Within plus or minus 1 code is the share of chips whose prediction is at most one step from the best code. This is the main score because one step is a tiny adjustment (2 mV, 0.2 percent or 5 mV).

### What is exact match and why is it lower than within plus or minus 1?
Exact match is the share of chips where the predicted code equals the best code exactly. On the held-out wafers it was 83.3 percent for bandgap, 50.6 percent for HSI and 89.4 percent for LDO. It is lower than the within plus or minus 1 score because the best code itself is partly decided by measurement noise, so even a perfect model would often be one step away. That is why plus or minus 1 is the fair measure.

### What is permanent importance (permutation importance)?
Permutation importance shuffles one input column and measures how much the error gets worse. A big increase means the model relies on that input. In this project the untrimmed value of each circuit was the most important input for its own code, and for HSI the oxide thickness reading came second.

### What is a baseline and why compare with one?
A baseline is a simple method used as a yardstick. If a complicated model does not beat a simple one, the complexity is not worth it. This project compared against the physics formula alone, a straight-line Ridge model and several tree models, plus the baseline-style HistGradientBoosting model that came with the dataset.

### What is residual learning (predicting the correction)?
Instead of predicting the code from scratch, the forest predicts the leftover difference between the best code and the physics estimate. The physics formula does the easy, well-understood part, and the forest only learns what physics misses. This gives a smaller and easier learning task and safer behaviour for unusual chips.

### What is one-hot encoding and how is the chip type given to the model?
Models need numbers, not names. The chip type is turned into two 0/1 flags (is MCU-B and is MCU-C); MCU-A is the case where both flags are 0. This is called one-hot style encoding. Chip type had almost no influence on the predictions.

### What is data drift and why does it matter?
Drift means the data seen in production slowly becomes different from the data the model was trained on, for example because the factory process changes. The model's accuracy then falls without any error message. This project saw a small version of this: new lots gave lower HSI accuracy. A production system would monitor the input values and accuracy and retrain when needed.

### What are calibration and conformal prediction?
A calibrated uncertainty means that when the model says "90 percent sure", it is right about 90 percent of the time. The tree-spread signal in this project is only a rough confidence signal, not calibrated. Conformal prediction is a method that gives prediction ranges with a guaranteed hit rate and is listed as a future improvement.

### What is an imbalanced dataset?
It means one outcome is far more common than the other. In this data 99.6 percent of chips pass the sort test and only 30 chips (0.36 percent) have a latent defect. For such outcomes plain accuracy is misleading, but the trim-code prediction itself does not suffer from this because its answers are spread over many code values.

### What is synthetic data and what are its limits?
Synthetic data is generated by a program that imitates real behaviour. It is useful for learning and demonstrating a method safely. Its limit is that it only contains the effects the generating program includes, so results on real silicon could differ and the model would need to be re-validated and retrained.

## 8. Chip and factory background (general)

### What is a fuse (one-time-programmable fuse)?
A fuse here is a tiny memory cell that can be programmed once and never changed. The trim codes of a chip are burned into fuses, so a fuse is permanent. That is why predicted codes are verified on the tester before burning. A chip's 64-bit fuse word holds all of its trim codes.

### What is a trim code?
A trim code is a small whole number that sets how much one circuit is adjusted. A centre code means no adjustment, and each step above or below the centre moves the circuit by a small fixed amount (2 mV for the bandgap, 0.2 percent for the HSI clock and 5 mV for the LDO). The project predicts three trim codes per chip: bandgap, HSI and LDO.

### What is a microcontroller (MCU)?
A microcontroller is a small computer on one chip, with a processor, memory and input/output circuits. It is used inside cars, appliances, tools and many other products. It needs an accurate reference voltage, a stable clock and a clean supply voltage to work properly, which are the three circuits this project trims.

### What is a wafer?
A wafer is a thin, round disc of silicon on which hundreds of identical chips are made at the same time. This dataset has 20 wafers. Chips on the same wafer share factory conditions, which is why the data is split by wafer.

### What is a die (a single chip)?
A die is one individual chip cut out of a wafer. Each row of the dataset is one die; there are 8,420 of them. The words die and chip are used for the same thing in these notes.

### What is a lot (a batch of wafers)?
A lot is a batch of wafers made together in the factory. A lot usually holds several wafers, and every lot behaves a little differently from other lots. This dataset has 5 lots (MA1, MA2, MA3, MB1 and MC1) and 20 wafers. Lots differ in their average behaviour: the average HSI code is about 34 in lot MA1 and about 80 in lot MA3. A new lot is the hardest test for the model, because it is a lot the model has never seen.

### What is a derivative (chip type)?
A derivative is a version of the same product family. Here they are MCU-A, MCU-B and MCU-C, entered in the app as the chip type.

### Why do chips differ from each other (process variation)?
Chip manufacturing involves thousands of precise steps, and small unavoidable variations in layer thickness, doping and temperature make each wafer and each die slightly different. This process variation moves the circuits' values away from their targets, which is why trimming is needed.

### What do the five process-monitor readings mean?
- Threshold voltage (NMOS and PMOS): the gate voltage at which a transistor switches on. It affects speed and many analog voltages.
- Sheet resistance: how much a thin conducting layer resists current, which affects resistors and timing.
- Oxide thickness: the thickness of the thin insulating layer under transistor gates; the HSI prediction relies on it noticeably.
- Relative carrier mobility: how easily charge moves through the silicon, where 1.0 is nominal and higher means faster transistors.

### What happens in the factory test flow?
After a wafer is made, each die is tested on a wafer sort tester (the sort test). Measurements are taken, the circuits are trimmed by burning fuses, and the die is tested again. Good dies are cut out and packaged, then tested again in a final test. Predicting the trim codes reduces the time spent searching for them at the tester, and tester time costs money.

### What is a binary search and why does trimming need about 20 steps?
Trimming by binary search tries a middle code, measures the result, then halves the remaining range, and repeats. A 6-bit code needs about 6 steps, a 7-bit code about 7 and a 5-bit code about 5, which matches the dataset's averages of 6.6, 7.6 and 5.6 steps (19.8 in total for the three circuits). A good first guess skips most of these steps.

### What are trim bits, and why do the three codes have different sizes?
The bandgap code has 6 bits (0 to 63), the HSI code 7 bits (0 to 127) and the LDO code 5 bits (0 to 31). More bits mean finer or wider adjustment. The HSI clock needs the widest range and finest steps, because a clock must be accurate to a fraction of a percent. The 64-bit fuse word holds all the codes of a chip.

### What is package drift?
After the chip is put into a package, mechanical stress and heat can shift its voltages slightly. In this data the LQFP100 package drifts the most (about 3.6 mV on the bandgap) and has the lowest final pass rate (about 90.6 percent).

### What is a latent defect?
A chip that passes the tests but is likely to fail later in the field. Here only 30 chips (0.36 percent) have one. This project does not predict defects; it only predicts trim codes.

## 9. Using the app

### How do I run the app on my computer?
Unzip the project, open the folder in VS Code, open a terminal and run these commands one after another. Create the environment with python -m venv .venv, activate it with .venv\Scripts\activate (on Windows), install with pip install -r requirements.txt and start the app with python -m streamlit run app.py. The app opens in the browser at http://localhost:8501. The commands must be run from inside the folder that contains app.py and requirements.txt.

### What does each tab of the app do?
- Single die: enter the chip type and eight measurements (or pick one of the demo dies), then see the three predicted codes, the HSI confidence meter, how the answer was made and the plain-English explanation.
- Project assistant: ask questions about the project and about the die currently shown.
- Batch (CSV): upload a file with many dies and download the predictions.
- About the model: the model card, accuracy figures and limitations.

### What columns does the batch CSV need?
One row per die with these columns: derivative, bg_untrim_V, hsi_untrim_MHz, ldo_untrim_V, pcm_vth_n_mV, pcm_vth_p_mV, pcm_rs_ohm_sq, pcm_tox_A and pcm_mobility_rel. The derivative must be MCU-A, MCU-B or MCU-C. Extra columns are kept in the output. If the file also has the true best codes (bg_trim_code_opt, hsi_trim_code_opt, ldo_trim_code_opt) the app also reports the accuracy. The file sample_dies.csv in the project is a working example with 9 dies.

### What are the demo dies?
sample_dies.csv holds 9 dies taken from a freshly generated dataset that the model never saw, so they are an honest example of how the model behaves on unseen data. They include the true best codes so the prediction can be compared.

### What do the confidence levels High, Medium and Low mean?
They come from the spread of the 300 trees' HSI predictions. A spread up to 1.022 is High, up to 1.406 is Medium and anything above is Low. On the brand-new dataset, dies in these groups were within plus or minus 1 code 97.0, 73.6 and 57.1 percent of the time. It is a rough guide and not a calibrated probability. Low confidence means the HSI code should be checked with a short search on the tester.

### What do the input warnings mean?
The app checks every input against the ranges seen in training. If a value is outside, a warning says the model is extrapolating and may be less reliable. Missing columns, an unknown chip type and empty or negative values are rejected with an error.

### Does the app need internet or an API key?
No. The trim model, the explainer, the batch tab and the About tab run fully on your computer. Only the optional LLM mode of the Project assistant needs an API key and internet, and the API is paid. Without a key the assistant works in offline mode, answering from these notes. Offline mode can only answer what is written in these notes, so adding sections to this file makes it smarter.

### How do I make the offline assistant answer better?
Edit project_knowledge.md. Each question is a heading that starts with three hashes, followed by its answer text. The offline search compares the user's question with the headings and text of every section, and headings count most, so write headings the way people would ask the question. Save the file and restart the app.

- Data: 8,420 dies, 42 columns, 20 wafers, 5 lots, 3 chip types (MCU-A 75 percent, MCU-B 15 percent, MCU-C 10 percent). Synthetic.
- Targets: bandgap 1.200 V (6-bit code, centre 32, 2 mV per step); HSI 16 MHz (7-bit code, centre 64, 0.2 percent per step); LDO 1.100 V (5-bit code, centre 16, 5 mV per step).
- Model: Random Forest, 300 trees per target, predicting the correction to a physics estimate.
- Held-out wafers, within plus or minus 1 code: bandgap 99.95 percent, HSI 82.3 percent, LDO 100 percent.
- New dataset with new lots (seed 777): bandgap 99.89 percent, HSI 75.9 percent, LDO 100 percent.
- Checks per chip: about 19.8 with the old search versus about 4.8 with the model on the held-out wafers, roughly 75 percent fewer.
- Hold-out test: 5 wafers (one per lot), 2,105 dies.

### Why are there several different HSI accuracy numbers?
They answer different questions, so they are not in conflict. About 54 percent is a plain straight-line formula in the data exploration. About 67 percent is the physics formula on the cross-validation wafers, and about 71 percent the same formula on the held-out wafers. About 80.5 percent is the Random Forest in cross-validation, 82.3 percent on the held-out wafers from known lots and 75.9 percent on a new dataset with new lots. When asked for one number, say about 82 percent on known lots and about 76 percent on new lots, and explain that new lots are the harder and more realistic case.

### What is the improvement over the physics formula alone?
On the held-out wafers the HSI within plus or minus 1 code went from 71.5 percent (physics formula only) to 82.3 percent (this model), exact match from 25.0 to 50.6 percent, and the average error from 1.10 to 0.72 codes. For bandgap (99.71 to 99.95 percent) and LDO (100 to 100 percent) the formula is already almost perfect, so the model adds little there. The real value of the model is the HSI.

### What software was used?
Python 3.12.3 with scikit-learn 1.8.0, numpy 2.4.4, pandas 3.0.2 and joblib 1.5.3 for the model, Streamlit for the app and the Anthropic library for the optional LLM mode.

## 11. More interview questions

### Q: Explain this project in one minute.
Chips come out of the factory slightly off target, so three circuits (a reference voltage, a clock and a regulator) are fine-tuned by burning trim codes into fuses. Finding the codes normally takes about 20 test steps per chip. I trained a Random Forest on 8,420 chips that predicts each code from pre-trim measurements and process-monitor readings, starting from a physics estimate. On held-out wafers it cut the average to about 4.8 checks per chip. Bandgap and LDO are almost always within one code; the clock is harder at about 82 percent, and about 76 percent on new lots. I wrapped it in a Streamlit app with input checks, a confidence signal and a plain-English explainer.

### Q: What was the hardest part?
The HSI oscillator. Its measurement is noisy and its relationship with the code is curved, so a straight-line model fails and even the best model reaches only about 80 to 82 percent within plus or minus 1. I handled it with a physics base, process-monitor inputs, wafer-grouped validation and a confidence signal that tells the user when to fall back to a short search.

### Q: Why Random Forest and not XGBoost or a neural network?
Random Forest was best on all three targets in wafer-grouped validation, needs little tuning and gives a natural confidence signal from its tree spread. A HistGradientBoosting model was about equal on HSI but worse on bandgap in the comparison, though it was only run with default-style settings, so I do not claim it is worse in general. A neural network would add complexity on a small tabular dataset.

### Q: What is data leakage and where could it have happened?
Leakage is giving the model information that already contains the answer. The fuse word matched the trim codes 100 percent, and every value measured after trimming is a consequence of the answer, so all of these were excluded. The model sees only values available before trimming.

### Q: Why is accuracy on new lots lower?
Lots differ in their average behaviour (for example the average HSI code is about 34 in lot MA1 and about 80 in lot MA3). A model trained on some lots has to guess for a new lot, and the HSI is the circuit most sensitive to such shifts. The suggested fix is per-lot calibration with a few dies measured by the old search.

### Q: What is per-batch calibration for new wafers (interview answer)?
For each new batch of wafers, trim a few dies with the old full search, compare the true codes with the model's predictions and shift all predictions of that lot by the average difference. It costs a few searches per lot and should recover much of the lost HSI accuracy. It was not implemented and is listed as the next improvement.

### Q: How would you put this into production?
Host the app and model on a company server, log every prediction and the later true result, monitor the input ranges and accuracy for drift, retrain offline when needed, keep the model file versioned with its model card, and keep a human or tester verification step before fuses are burned.

### Q: How do you know the confidence signal is useful?
Dies with a low tree spread were within plus or minus 1 code 97.0 percent of the time on new data, against 57.1 percent for high-spread dies. The signal separates reliable from unreliable predictions well, but it is not a calibrated probability, so it is described as a rough guide.

### Q: Why did you remove die position and the SRAM failure count?
They were tested and gave no accuracy gain. Position had almost no straight-line link with the codes, and removing them keeps the model simpler and the app easier to use.

### Q: What does the model do for chips it has never seen the type of?
Nothing reliable. The app rejects unknown chip type names, and warns when values are outside the training range, but a new design would need new data, validation and probably retraining.

### Q: Is the physics estimate a cheat?
No. It is ordinary engineering knowledge: the step size of each code is known, so an untrimmed error converts into a code by arithmetic. Using known physics is good practice. It makes the model smaller, more robust and easier to explain, and its contribution is measured honestly by also reporting the physics-only baseline.

### Q: What would you check if accuracy suddenly dropped in production?
First the inputs: are the values inside the training ranges, has a process-monitor reading drifted, is it a new lot or a new chip type. Then compare the physics-only error with the model error, check the tester measurement for changes, and if needed run per-lot calibration or retrain.

### Q: What are the risks of the assistant?
An LLM can state things confidently that are not true. This one is told to answer only from the project notes, never to invent numbers and to say when it does not know. Its answers are explanations only and never affect the model's predictions. The offline mode shows text straight from the notes, so it cannot make things up at all.

### Q: What did you learn from this project?
That the scoring method matters as much as the model (wafer-grouped splitting and a fresh dataset exposed the real HSI weakness), that simple physics knowledge combined with machine learning beats either alone, that data leakage must be actively hunted for, and that being honest about limitations makes a project more trustworthy.

## 12. Fuse map: building and checking the fuse word (added in version 3)

### What is the fuse word and what is inside it?
Each MCU stores its settings permanently in a 64-bit fuse word. The fields, from the lowest bit: BG_TRIM (bits 0 to 5), HSI_TRIM (6 to 12), LDO_TRIM (13 to 17), TS_CAL1 (18 to 29, the temperature-sensor reading at 30 degrees C), FLASH_SIZE (30 to 31: 0 is 256 KB, 1 is 512 KB, 2 is 1 MB), PERIPH_EN (32 to 39, which peripherals are switched on), TEMP_GRADE (bit 40, 1 means automotive), DEBUG_LOCK (bit 41, must be 1 in production), RDP (bit 42, read-out protection) and RESERVED (43 to 63, must be 0). The three trim codes and TS_CAL1 are different for every die. The other fields are fixed by the chip type: MCU-A has 512 KB flash, mask 0xFF and no read-out protection; MCU-B has 256 KB, mask 0x3F and none; MCU-C is automotive with 1 MB, mask 0xFF and read-out protection on.

### How does the app build and check a fuse word?
The Fuse map tab packs the three predicted trim codes, the TS_CAL1 value you enter and the fixed settings of the chip type into the 64-bit word, shows it in hex with every field decoded, and runs the rule check on it. You can also paste any fuse word, or upload a CSV of fuse words, and get a plain-English list of what is wrong and how to fix it.

### Why are the fuse bits decided by rules and not by machine learning?
Fuses are one-time programmable, so a wrong bit cannot be undone, and some bits are security bits (debug lock, read-out protection). Security and key fuses must stay on deterministic, auditable rules. In this project the machine learning model only suggests the three trim codes, and even those must be verified on the tester before anything is burned. Every other fuse bit comes from the chip-type rules in the fuse schema.

### How well does the fuse check work?
On the dataset's labelled audit file (1,500 fuse words, 406 with injected errors) the checker flagged 406 of 406 errors with 0 false alarms and named the correct error type every time. On a second file generated with a different random seed (1,500 words, 383 errors) it flagged 383 of 383 with 0 false alarms. It could also rebuild 100 percent of the error-free fuse words exactly from the trim codes, the TS_CAL1 value and the chip type. The error types are: missing debug lock (127 cases in the first file), peripheral mask mismatch (76), reserved bit set (72), wrong flash size (64), corrupted trim field (61) and missing read-out protection on the automotive chip (6). Two honest caveats: a corrupted trim field can only be detected when the expected codes are available (from the tester, or compared with the model prediction), and the rules were written from this dataset's schema, so the perfect score shows that the rules cover the injected error types, not that they cover every possible real-world error.

### What is TS_CAL1?
A 12-bit per-die measurement of the on-chip temperature sensor at 30 degrees C. It is stored in the fuse word but it is measured, not predicted by this model. In the training data it ranges from about 955 to 1104 counts.

### Q: What happens if a wrong fuse is burned?
It cannot be undone. A missing debug lock leaves the debug port open (the part could be read out or tampered with), a missing read-out protection on an automotive part is a security and safety risk, and a wrong flash size or peripheral mask means the part does not behave as the product it is sold as. That is why the checks are rule-based and why predictions are verified before burning.

## 13. Transfer learning to a new chip type (added in version 3)

### What is transfer learning and why does it matter for derivatives?
A derivative is a variant of a base chip that shares most of its circuits. Transfer learning means reusing what a model learned on the well-characterised chips (here MCU-A and MCU-B) for a new chip type (MCU-C) so that little or no new characterisation data is needed. The project's concept document recommends organising models by circuit block (the bandgap, the oscillator, the regulator) instead of by product, so that a new derivative needs only a small fine-tune.

### What experiment was run and what did it show?
MCU-C was treated as a new chip type. Four set-ups were compared on one MCU-C wafer (421 dies), then the two MCU-C wafers were swapped and the results averaged: the physics formula only; a model trained on MCU-A and MCU-B only with no MCU-C dies at all (zero-shot); the same model plus k dies from the other MCU-C wafer (k = 10, 25, 50 and 100, four random draws each, extra weight 20 on those dies as in the dataset's baseline script); and a model built from scratch using only those k MCU-C dies. Share of dies within plus or minus 1 code:
- HSI: physics formula only 69.5 percent; zero-shot 78.5 percent; adding 10, 25, 50 and 100 MCU-C dies gave 76.4, 76.1, 75.1 and 76.8 percent; adding all 421 gave 79.1 percent; from scratch with 10, 25, 50 and 100 dies gave only 67.6, 70.1, 72.6 and 72.4 percent.
- Bandgap: 99.9 percent zero-shot (physics only 99.6); LDO: 100 percent in every set-up.
- Mean absolute error on HSI: 1.13 codes for the formula, 0.87 for zero-shot, 0.82 with all MCU-C dies.

### What is the conclusion of the transfer experiment?
For predicting trim codes, the model already works on a new chip type without any new data: 78.5 percent zero-shot versus 79.1 percent with a full wafer of MCU-C data. Adding a few MCU-C dies did not help (the draw-to-draw spread was 2 to 4 points, so those differences are noise, or slightly worse). Building a model from only a few MCU-C dies is clearly worse than reusing the model trained on the other chips. So the transfer idea is confirmed in the sense that knowledge is reused, but fine-tuning was not needed. The likely reason is that the three chip types use the same bandgap, oscillator and regulator circuits, so the link between an untrimmed value and its best code is the same, and the physics estimate carries over. Where chip-type-specific fine-tuning should matter is behaviour that differs by package, such as the shift between wafer sort and final test; the dataset's baseline shows this for MCU-C (the shift error improves from 1.73 mV to 0.86 mV with 50 MCU-C dies). That drift-aware target is not built in this project and is the natural next step.
Caveats: only two MCU-C wafers (842 dies) exist, there were four random draws per setting, and the data is synthetic.

### Q: Did you apply transfer learning?
Yes, I tested it. I treated MCU-C as a new chip type and trained on MCU-A and MCU-B only. It reached 78.5 percent within plus or minus 1 code on HSI without seeing any MCU-C die, almost the same as 79.1 percent with a full MCU-C wafer, while a model built from scratch on 50 MCU-C dies got only 72.6 percent. So the knowledge transfers without fine-tuning for trim codes. I expect fine-tuning to matter for package-dependent drift, which I would add next.
